# Firebird Driver for sysbench

## Overview

This fork adds Firebird database support to sysbench, enabling the same
OLTP benchmarks used for MySQL and PostgreSQL to run against Firebird 3, 4,
and 5.

The driver is written in C against `libfbclient` (legacy ISC API). All
Firebird-specific code lives in `src/drivers/firebird/`. The OLTP Lua scripts
and core sysbench code remain byte-identical to upstream — the only upstream
edits are additive (registering the driver in the build system).

Repository: https://github.com/ZlatanOmerovic/firebird-sysbench
Upstream: https://github.com/akopytov/sysbench

## MVP Scope (Phase 1)

### What's delivered

- `src/drivers/firebird/drv_firebird.c` — full driver implementation
- `src/drivers/firebird/Makefile.am` — build integration
- `m4/ac_check_firebird.m4` — autoconf macro to detect libfbclient
- Build system wiring in `configure.ac`, `src/Makefile.am`,
  `src/drivers/Makefile.am`, `src/db_driver.h`, `src/db_driver.c`
- Firebird DDL branch in `src/lua/oltp_common.lua`
- Working OLTP benchmarks: `oltp_point_select`, `oltp_read_only`,
  `oltp_read_write` — with and without prepared statements
- Tested on Linux x86_64 against Firebird 5.0

### Command-line options

```
--firebird-db        Database connection string (e.g. localhost:/tmp/sbtest.fdb)
--firebird-user      User name (default: SYSDBA)
--firebird-password  Password (default: masterkey)
```

### Driver capabilities

```
multi_rows_insert = 0   (Firebird has no multi-row VALUES syntax)
prepared_statements = 1 (XSQLDA-based)
auto_increment = 0      (uses IDENTITY columns instead)
needs_commit = 1        (Firebird has no auto-commit)
serial = 0              (not supported)
unsigned_int = 0        (not supported)
```

### SQL dialect handling

All SQL dialect differences are handled inside the driver or in a single
Lua DDL branch. The OLTP query templates are unchanged.

| Feature | How it's handled |
|---|---|
| Auto-increment | `GENERATED BY DEFAULT AS IDENTITY` (FB 3+) in Lua DDL |
| Parameters | `?` markers — same as MySQL, no conversion needed |
| Transactions | Driver intercepts `BEGIN`/`COMMIT`/`ROLLBACK` strings and translates to ISC API calls |
| Multi-row INSERT | `multi_rows_insert=0` — sysbench bulk layer sends individual INSERTs |
| DROP TABLE IF EXISTS | Native in FB 5.0+ |

### Stability milestone

64 threads, 10-minute `oltp_read_write` run without errors.

## Post-MVP Roadmap

### Phase 2 — EXECUTE BLOCK Bulk Loading

**Problem:** The `prepare` phase (loading test data) is slow because Firebird
lacks multi-row INSERT. With `--table-size=1000000`, prepare can take minutes
of individual INSERT round-trips.

**Solution:** Add `--firebird-bulk-method` option:
- `single` (default) — current behavior, one INSERT per round-trip
- `execute-block` — batch N inserts into an EXECUTE BLOCK:

```sql
EXECUTE BLOCK AS BEGIN
  INSERT INTO sbtest1(k, c, pad) VALUES (5, '...', '...');
  INSERT INTO sbtest1(k, c, pad) VALUES (3, '...', '...');
  ...
END
```

This is a driver-level optimization that doesn't touch shared sysbench code.
Expected 5-10x speedup for the prepare phase.

**Implementation:** Override the `query()` path during bulk insert to buffer
rows and flush them as EXECUTE BLOCK statements. The batch size should be
tunable (e.g. `--firebird-bulk-batch-size`, default 100).

### Phase 3 — Firebird Architecture Comparisons

Firebird supports three server architectures: Classic, SuperServer, and
SuperClassic. sysbench is the ideal tool to measure their thread-scaling
characteristics.

**Deliverable:** A benchmark script and results document comparing:
- Classic vs SuperServer vs SuperClassic
- Thread scaling from 1 to 128 threads
- `oltp_read_only` and `oltp_read_write` on identical hardware

### Phase 4 — Firebird Version Comparisons

Run identical benchmarks across Firebird 3.x, 4.x, and 5.x to produce
the first publicly reproducible cross-version performance data.

**Deliverable:** Automated benchmark runner (shell script or Docker Compose)
that runs the same workload against multiple Firebird versions and produces
a comparison report.

### Phase 5 — Additional OLTP Scripts

Extend benchmark coverage to all bundled OLTP scripts:
- `oltp_insert`
- `oltp_delete`
- `oltp_update_index`
- `oltp_update_non_index`
- `select_random_points`
- `select_random_ranges`
- `bulk_insert`

Some of these may require additional Lua DDL adjustments.

### Phase 6 — Upstream Merge

Submit a PR to `akopytov/sysbench` to merge Firebird support upstream.

**Prerequisites before submitting:**
- Driver stable with real-world usage
- CI passing with Firebird in the test matrix
- Documentation in upstream README format
- SHA-256 checksums of Lua scripts match upstream
- Clean git history (additive changes only)

### Phase 7 — OO API Migration (Optional)

The current driver uses the legacy ISC API (`ibase.h`). Firebird 3+ offers
a newer object-oriented API with advantages:

| Feature | ISC API | OO API |
|---|---|---|
| Batch execution | Not available | `IBatch` interface |
| Scrollable cursors | Not available | `IResultSet` with scroll |
| XSQLDA size limits | 65535 fields | No limit |
| Error handling | Fixed 20-element status array | Unlimited `IStatus` |

Migration to the OO API would enable batch execution (replacing EXECUTE BLOCK)
and remove legacy limitations. This is optional and only worthwhile if the
ISC API becomes a bottleneck.

### Phase 8 — Docker Compose Reproducibility Kit

Ship a Docker Compose setup for one-command benchmarking:

```
docker compose up --profile firebird-vs-postgres
```

Containers:
- Firebird 5.0 server
- PostgreSQL 17 server
- sysbench runner (pre-built with both drivers)
- Results collector (produces comparison tables)

### Phase 9 — Windows Native Support (Optional)

Firebird runs natively on Windows. Investigate whether the driver can be
built with MinGW or MSVC for native Windows sysbench support. Currently,
Windows users must use WSL2.

## Design Principles

1. **All Firebird code in one directory** — `src/drivers/firebird/`
2. **Upstream Lua scripts byte-identical** — except the DDL branch in
   `oltp_common.lua`, verifiable with `git diff`
3. **SQL dialect differences inside the driver** — never in workload scripts
4. **Only additive upstream edits** — registering the driver in build files
5. **ISC API for maximum compatibility** — works with Firebird 3, 4, and 5
